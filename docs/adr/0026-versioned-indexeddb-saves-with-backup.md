# Use Versioned IndexedDB Saves With a Backup

## Context

长期境界进度、局内断点、PWA 更新和离线内容状态都需要异步、可靠且可迁移的本地存储。把所有数据写进同步的 `localStorage` 难以支持较大的结构化状态，也缺少可靠的事务与恢复策略。本地存档无需承担可信竞技防作弊。

## Decision

- 使用 IndexedDB 保存长期进度、历练断点和内容下载状态。
- `localStorage` 只保存音量、语言等可以轻易重建的极小设置。
- 每份存档包含 `schemaVersion`、游戏版本、写入时间和用于发现损坏的校验值。
- 采用“当前存档 + 上一份有效备份”双槽策略。新内容完整写入并验证成功后，才将其提升为当前存档。
- 启动时若当前存档损坏，自动尝试恢复上一份有效备份，并向玩家明确说明。
- 存档结构通过集中、逐级且可重复执行的迁移函数升级，例如 `v1 → v2 → v3`；版本判断不得散落在领域逻辑中。
- 导出文件携带格式与版本信息；导入前预检完整性，并展示境界、游玩时间和来源版本供玩家确认。
- 不加密本地存档。校验只用于发现损坏，不宣称能够阻止修改或作弊。

## Consequences

- `SaveRepository` 的浏览器适配器必须处理事务失败、容量不足、被拒绝和页面关闭时的写入边界。
- 存档迁移和备份恢复属于发布阻断级测试范围。
- 长期存档、历练断点与内容缓存需要独立记录和生命周期，不能用一个巨型对象每次整体覆盖。
- 玩家仍需通过导出文件自行完成跨设备迁移。
